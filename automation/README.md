# Automation State

`automation/state.json` stores the persistent ranked performer queue, active performer, shuffled no-repeat surah queue for that performer, completed performer/surah pairs, unavailable pairs with reasons, shuffled no-repeat background queue, cycle number, cached playlist IDs, pending post-upload checkpoint, last successful upload time, last success, and recent failures.

The order comes from `config/automation_reciters.json`; alternate recordings of one performer share completion history. A performer is retained until every available surah is completed. Queue exhaustion never restarts completed performers. Schema-v1 migration resets only the mixed-performer surah queue, retains independent background/playlist state, and imports known upload completions. The deployed migration also recovered successful uploads from Git history. YouTube separately confirmed that the earlier Taha uploads `PSFmSdvTQus` (Alafasy) and `ZVNDWjiv6Sk` (Al-Tunaiji) are processed and public; those pairs are included despite their later playlist-step failures.

The workflow commits successful production state and durable post-upload checkpoints even after a later step fails. Manual dry runs preserve state unless `advance_state=true`. Post-upload recovery reuses the uploaded video, marks its surah complete, and leaves the next render for the next interval. Scheduling uses `last_success_at`, with a legacy Git timestamp fallback, and retries pending checkpoints at the next scheduled check.

Do not edit this file while a workflow is running. Rendered videos, thumbnails, audio downloads, logs, and credentials are never stored here.

Upload uniqueness: the pending checkpoint may have `video_id=null` while a durable reservation exists. Its `pair_key` identifies the performer/surah, independently of recording variants. Production must publish that reservation before sending any video bytes. A returned video ID is also checkpointed immediately. If a runner disappears or an upload response is lost, the next run searches the authenticated channel's uploads for the exact pair marker. No match means the outcome is unresolved, not permission to upload again. The workflow keeps the reservation and reports failure until reconciliation succeeds. Never clear an unresolved reservation merely to retry: inspect the channel first. Playlist membership is checked before insertion, and description updates retain the pair marker.

Playlist recovery retries temporary `playlistNotFound`/`videoNotFound` responses after creation, YouTube 409/429/5xx responses, and connection failures up to five attempts with 1/2/4/8-second delays. Membership is checked before every insertion attempt; authentication failures still fail immediately. The selected playlist ID is saved before insertion, and the cache is shared by performer across recording variants. Successful checkpoint recovery sends a Telegram completion message so an earlier failure alert is followed by its resolution. Notification outages do not invalidate a completed recovery.
